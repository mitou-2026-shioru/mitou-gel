# GelLink Device API v1

入力アプリケーションと物理制御を分離するためのWi-Fi HTTP APIです。M5Stackの機種、GPIO、ヒーター・ポンプ・弁・センサ構成に依存する処理はファームウェア側に置きます。

## エンドポイント

| Method | Path | 動作 |
|---|---|---|
| GET | `/v1/status` | 現在の実測値、制御目標、異常状態を取得 |
| POST | `/v1/state` | 正規化した温度・硬さの指令を受け付け、適用した命令IDと状態を返す |

要求・応答はUTF-8のJSON、`Content-Type: application/json`。成功はHTTP 200、不正値や順序違反は400、未知のパスは404とします。POSTはJSONを検証してから出力を変更し、エラーでは出力を有効にしません。

## 制御要求

```json
{
  "version": 1,
  "command_id": "18FC49A8-A0C7-4F65-A26D-FD4C362D2BFE",
  "session_id": "17355A7D-4A49-4669-A928-27346D7480A6",
  "sequence": 2,
  "temperature": 0.65,
  "stiffness": 0.85,
  "enabled": true,
  "ttl_ms": 6000
}
```

- `temperature` / `stiffness`: 有限数の0〜1。温度の℃、剛性や圧力への変換はデバイスの校正表で決めます。
- `enabled`: falseはヒーター・ポンプを停止し、機構に応じて弁を安全側へ戻します。温度0.5を能動維持する指令ではありません。
- `command_id`: 命令ごとのUUID。POST応答の `accepted_command_id` が一致しない場合、iPhoneは制御失敗として扱います。
- `session_id`: 接続設定ごとのUUID。新しいセッションは必ず `enabled=false` から開始し、制御権を確立します。別セッションからの有効化要求を拒否します。
- `sequence`: セッション内で単調増加する整数。最後に受け付けた番号以下の命令を拒否します。停止より先に送られた有効化要求が遅れて届いても再有効化しないためです。
- `ttl_ms`: 1000〜6000 ms。デバイスで受け取った時点から単調時計で計測します。時計同期は不要です。iPhoneは固定2秒周期で命令を更新し、遅れた周期は飛ばします。

自動入力の2軸は直近10 / 30 / 60秒の触覚候補をサンプル平均した値です。窓長や生体情報・音声・文字起こし本文をM5へ送りません。手動入力は平均を省略し、開始と停止は周期を待たず送信します。詳細は [ことば入力と時間窓](VOICE_AND_WINDOW.md) を参照してください。

新しい接続セッションの `enabled=false` 要求を受け付けると既存出力を停止します。実機では、終了したセッションIDの管理や、通信処理と制御ループの排他にも配慮してください。

## 状態応答

GETと成功したPOSTは同じ形式で返します。以下のキーを全て返し、取得できない値にはJSONのnullを使います。

```json
{
  "version": 1,
  "accepted_command_id": "18FC49A8-A0C7-4F65-A26D-FD4C362D2BFE",
  "state": "active",
  "actual_temperature_c": 32.4,
  "actual_pressure_kpa": -18.0,
  "temperature_target": 0.65,
  "stiffness_target": 0.85,
  "error": null,
  "simulated": false
}
```

| state | 意味 |
|---|---|
| `idle` | 出力停止・待機 |
| `active` | 期限内の指令を制御中。目標に到達したことを意味しない |
| `expired` | TTL切れで出力停止 |
| `fault` | センサ異常・過熱・圧力異常などで出力停止 |

`actual_pressure_kpa` は大気圧基準のゲージ圧で、真空方向を負とします。`temperature_target` と `stiffness_target` は正規化指令です。温度未計測ならnullで返しますが、実ヒーターは温度センサなしで有効化しないでください。`fault` では `error` に異常理由を返し、物理的な異常解除と明示的な再開を要求します。

## デバイス側で必要な制御

1. 起動直後、Wi-Fi初期化中、リセット中は出力OFF。
2. JSONを検証し、UUID・順序・範囲・TTLを確認した後に目標値を更新。
3. 温度センサを読み、閉ループ制御で設定温度へ近づける。人体接触面の許容範囲を実機評価で決定し、ソフトウェア制限と独立の遮断手段を用意。
4. ジャミングの圧力・駆動時間・弁の状態を制御し、リークやポンプ過負荷に対応。
5. 通信処理と独立したループでTTL、センサ異常、過熱、圧力異常を監視。異常や期限切れで停止。
6. 最新の実測・目標・状態をAPIで返す。

`tools/mock_m5stack.py` はこのAPIの通信相手として使用できます。常に `simulated=true`、実測値nullを返し、物理出力を動かしません。模擬TTLの状態は取得・操作時に更新されます。実機の監視ループの代わりにはなりません。

## m5-dual-control v3のLAN接続

設定の「M5ポンプ・ヒーター」は、上記JSON APIとは別の通信方式です。別管理の`m5-dual-control`の`LanTransport.h` / `BleWire.h`に対応します。既存APIと模擬サーバーには「GelLink API / 模擬サーバー」を使います。

- M5画面のLAN URL（HTTP、ポート80）と8桁のLAN PINを使用。各要求の`X-M5-Key`ヘッダーでPINを渡します。PINはメモリ内のみで、設定保存・CSVには含めません。
- `GET /api/state`: v3の20バイト状態。測温値、正規化目標、適用ポンプ値、ヒーター有効・加熱中・準備完了フラグ、異常、操作セッション、更新カウンターを検証します。
- `POST /api/command`: 16バイトの命令を32文字の小文字16進数にした`text/plain`。応答の12バイトACKと20バイト状態を確認し、セッション・連番が一致しない応答や古い更新カウンターを拒否します。
- 接続は状態取得のみ。明示的な「出力開始」で新規セッションの`HELLO`、必要な`TARGET` / `PUMP`、`HEATER 1`を順に送ります。他の操作セッションを引き継いだり自動的に奪ったりしません。
- 温度候補は`TARGET`へ、硬さ候補は`PUMP`へ渡します。分解能は0.0001。物理目標は25〜50℃、ポンプは0 / 0.38 / 0.71 / 1の4段階（同距離なら小さい値）。温度0でも加熱制御は有効で、停止は別命令です。
- 出力更新は2秒周期。操作権を保有している間は450ms周期の`PING`を独立して実行し、更新指令と直列化します。要求タイムアウトは1秒、M5のリースは2秒。古い状態を生存確認として採用しません。
- 停止は進行中の更新を取り消し、より大きな連番の`STOP`と`RELEASE`を送ります。操作権喪失・通信断・異常・本体B操作から自動再開しません。`STOP`はM5側では他セッションにも有効なため、所有権を取得できなかった接続からは送信しません。
- 複数の指令の途中で失敗した場合も、所有権を確認できているセッションへ停止を試み、生存確認を終了します。停止応答が届かない場合はM5側の2秒監視が必要です。
- UIは目標℃、適用ポンプ設定、実測温度、ヒーター状態を表示し、診断表示ではPPS電圧も表示します。このM5は圧力を返さないため、実測圧力は生成しません。

CSVの`connection_kind`で接続方式を識別し、要求した正規化値とは別に受理した目標・適用ポンプ値を記録します。M5方式の`command_id`は、全指令のACKと適用状態を確認した後に発行するアプリ内の処理IDです。M5の32ビット連番やUUIDの応答を意味しません。

`Tests/Fixtures/m5-lan-v3.json`は提供されたM5のC++ヘッダーで生成した参照データです。Swiftテストで実際の命令・応答形式との一致、PIN拒否、途中失敗後の停止、遅延応答、本体B操作、別端末との競合、接続維持を検証します。実機の電波状況・ポンプ・ヒーターの動作は別途確認が必要です。
